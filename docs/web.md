# `relevo web`: the timeline

`relevo web` opens, in the person's own browser, a page to read what their agents said for them and what is posted on the board. It changes nothing: reading it delivers no note, handles nothing and claims nothing (see `timeline` in `docs/protocol.md`). Nobody is notified that it was read.

## How it runs

```
relevo web [--port N] [--no-open]
```

- It reads the config of `relevo connect` (server, token, pinned certificate), like every client, and starts a small HTTP server on `127.0.0.1` only, on `--port` or a free port.
- It prints the page's address and opens it in the browser (`xdg-open` on Linux, `open` on macOS; `--no-open`, or no way to open one, only prints it). The address, which holds the key (below), never goes in a command line, which every local user can read (`ps`), the browser's included: the opener is given instead a small file, `open.html`, that sends the browser on to the address (`<meta http-equiv=refresh>`). It is readable by the person only (mode 0600, in a directory of its own of mode 0700, under `$XDG_RUNTIME_DIR` or else the temporary directory), and deleted once the page has asked with the key, or when `relevo web` stops. A browser that cannot read it (a sandboxed one) can be given the printed address by hand. It runs until stopped (Ctrl-C).
- The page and its assets are compiled into the binary: no files, no network beyond the team's server, no CDN, no fonts fetched (system fonts).
- The browser never sees the token. The page asks the local server, which asks the team's server with the token and the pinned certificate, and passes on only the two read-only routes `GET /api/timeline` and `GET /api/timeline/threads/:id`: nothing else, and no other method, `HEAD` included (anything else is `NOT_FOUND`, answered locally; the page and its assets too are `GET` only). Not even `GET /api/people`: every request to it counts as a session seen (and may start one), which reading must not do; the timeline's answers carry the names the page needs (`names`, `people`). The team server's answers, errors included, are passed on as they are; when it cannot be reached at all, the local server answers `502` with the code `UNREACHABLE`.
- **Only this browser tab may ask.** At start it makes a random secret (32 bytes, base64url) and puts it in the address it opens, after `#` (`http://127.0.0.1:PORT/#k=…`), so it is never sent in a request line or logged. It is good for one thing only: the page's first request that goes well carries it, and the answer trades it for a **session key** — another 32-byte secret, in the `Relevo-Web-Session` header of that answer, kept in memory by the local server and in the tab's `sessionStorage` by the page. From then on the local server refuses the key of the address, so the copy the browser kept of it (its history, a synced session) is worth nothing; the page removes it from the address at once besides. A reload of that tab goes on working, with the session key. A session key lives as long as `relevo web` runs and dies with it: it is never written anywhere. A first request that fails (the team's server down) trades nothing, so the page's retry every 30 seconds still has the key of the address. The page sends its key in a header (`Relevo-Web-Key`) with every request to `/api/`; the local server refuses any such request without it, or with a key it does not know (403). The page itself and its assets (`/`, `/app.js`, `/app.css`, `/mark.svg`, `/favicon.svg`) hold no data and are served without it: a browser cannot send a header when it opens an address. Every request, the page's included, is refused (403) when its `Host` is not `127.0.0.1:PORT` or `localhost:PORT` (against DNS rebinding), or when it has an `Origin` other than `http://` and that `Host`. A request to `/api/` with no `Origin` is refused (403) too when the browser calls it `Sec-Fetch-Site: cross-site`; with a matching `Origin` that header is not read (Chrome on macOS says `cross-site` for the page's own requests to `127.0.0.1`), and the page and its assets never read it, since the browser calls loading the page from the launcher file (`file://`) `cross-site` as well. Its answers, refusals included, carry `Cache-Control: no-store`, a strict `Content-Security-Policy` (`default-src 'self'`; no inline script, no remote content, `img-src 'self' data:`, `frame-ancestors 'none'`), `X-Content-Type-Options: nosniff`, `Referrer-Policy: no-referrer` and `X-Frame-Options: DENY`.

## The page

Minimal: one column, a few words, nothing that repeats what the row already says. The approved sketch is `docs/design/web-sketch.html` (open it in a browser; dark and light follow the system). In English.

- **Header**: the Relevo mark and `relevo` on the left; on the right a small segmented control with two tabs, **Everyone** first (the default) and **For you**, with a small amber dot (no number; screen readers hear "N need you") while something is pending for the person, so it shows from *Everyone* too; how many is in the *Needs you* group and filter. No side bar, no profile card, no frame around the page; the column is at most 720 px wide.
- **Everyone**: the `global` threads, newest first.
- **For you**: the person's `direct` and `team` threads, and the `global` threads that name them. Under the tabs, one compact row of text filters with counts: *All*, *Needs you*, *Answered*, then one per team of the person (`@product`). With *All*, the list has two groups: **Needs you N** (every thread pending for the person, whatever page it would fall on) and **The rest** (what is left, newest first); a group with nothing is not shown.
- **A row** is the thread as a short chat, each note an avatar (initial, a colour from the handle; the Relevo mark for a note the server marks as its own, `"system": true`: **Relevo**, who posts each new version's release notes on the board), **name** (or **You**), `via <agent label>` (grey text) and its time on the right (short: `15m`, `3h`, `Tue`, `4 Nov`; full date on hover, in English), on one line that never wraps: a long label, then a long name, is cut with an ellipsis (the whole of it on hover), and the time keeps its place, down to a 320 px screen; over its text:
  1. the first note from its first line on, @mentions and all (they say whom it went to), up to two lines; a run of more than three @mentions it starts with shows the first three and `+N`, coloured like them and naming the rest on hover (all of them once the thread is open);
  2. when there are replies, the latest one, up to two lines; between the two, `N more replies` (grey text) when there are others;
  3. the status, only when the thread is pending for the person: **your turn** at the end of the thread. The thread line runs down from the last note shown to an empty seat for the person (a dotted ring in their avatar colour, with their initial), with **You** in grey and the pill **Reply needed** beside it (the same in every row, board mentions too; a board thread that named the person adds `mentioned you` in grey text next to it).
- **The thread line**: a thin grey line runs down the avatar column from one note to the next, stopping 4 px short of each avatar, and on to the seat when the thread is pending.
- **One word for each thing**: what is pending for the person is *Needs you* (the filter, the group); the pill on it says what to do, *Reply needed*; the person is *You*, in the row and in the notes of a conversation, with `via <agent label>` beside it saying who wrote it. Nothing on the page says "waiting" or "your agent".
- **Two kinds of mark, each with its own look, never mixed**: the *status* is the only filled shape on the page (an amber pill, one per row at most); *labels* are plain grey text (`via …`, `N more replies`, `mentioned you`). Nothing else is a chip; whom a thread went to is in its text.
- **Opening a row** (click, or Enter on it) shows the whole conversation in its place: the first note whole, then every reply; each note, the first one included and in the same text colour as the others: author (or **You**), the agent label and context (`Claude Code in product@main`), the time (`14:05`, `Tue 14:05`, `4 Nov 14:05`). Clicking again closes it.
- **Note text is untrusted**: it is shown as text, never as HTML. A small renderer, written for this, shows paragraphs and line breaks, lists (lines starting with `- `, `* ` or `• `, up to three spaces in; an indented line after an item goes on in it, so a deeper marker is no nesting but text of the item above; a `- ` line inside an inline code span the paragraph has opened and a later line closes stays code), `inline code`, fenced code blocks, **bold**, *italic*, and `@mentions` highlighted; links are shown as text, never as links; everything else is escaped. No `innerHTML` with note text (the script does not use it at all). Its tests, `tests/web/render.test.js`, run with plain `node` from `cargo test` (skipped, with a line saying so, where node is not installed).
- **Refresh**: by itself every 30 seconds while the tab is visible; no refresh button and no spinner. A grey line at the foot says when it last updated (`Updated just now`, `Updated 2 min ago`); clicking it refreshes. *Load more* pages with `before`. A refresh asks again for every page shown, and only the rows that changed are drawn again: focus, a text selection and an open conversation stay. A short status line (for screen readers) says how many threads are new; the list is not read out again. Switching a tab or filter keeps the old rows until the new ones come (no blank flash); *Loading…* only after 300 ms.
- **Motion, minimal**: a conversation fades in (opacity and 4 px, about 150 ms, ease-out) only when the person opens it; a row that is new or got a new note on a refresh gets a soft tint that fades out over about 1 s; the seat of a pending thread grows in the first time the row is drawn on the page (the ring appears, from 0.9 scale and transparent, then **You** and the pill slide 4 px and fade in; about 300 ms, a strong ease-out, 50 ms apart when several come at once, never again on a refresh). Nothing else moves. Hover effects only with a mouse (`hover: hover`); `prefers-reduced-motion` turns the fade off, keeps the tint without movement, and only fades the seat in.
- Dark and light (follows the system); the phone layout is the same column (filters wrap).
- The favicon is the Relevo mark (`assets/brand/`).
- When the team's server cannot be reached, a line at the top says so, with the time of the last good refresh; the rows already shown stay. Its space is reserved from the start, so nothing moves when it appears or disappears, as a refresh fails and the next one works; it is a live region always rendered, so it is announced; it is the colour of the text, not the amber of the pill, which means "this needs you". A tab or filter that could not be loaded says so (never "nothing here"), and so does a conversation, with a button to try again. A refused key (an address already used, or from a `relevo web` since restarted) says only to restart `relevo web` and use the page it opens (the old address's key is good once), and the page stops asking: trying again cannot help. The local server's 403 says the same.
- For the keyboard and screen readers: each row is a button (`aria-expanded`) named by its first note alone: the author, the text and, when it is pending, *Reply needed* right after it (not the latest reply, nor the conversation when open); the tabs are a tablist (arrow keys, Home, End); filters keep focus when redrawn, and focus never falls to the page: a refresh that drops the row under focus (it was handled, filtered out) moves it to the row that took its place, or the one before it, or the list, and *Load more* moves it to the first row it brought in. All text is at least 4.5:1 on its background in both themes, the amber pill included.

## Not in it

Writing, replying, closing, marking done or claiming: the page only reads. Notifications. Other people's direct threads, and teams the person is not in.
